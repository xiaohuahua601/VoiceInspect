# VoiceInspect

## 工业设备多模态辅助诊断与故障闭环平台

建议副标题：

> 以现场证据为输入，以可追溯知识为依据，以人工确认为边界。

讲解重点：VoiceInspect 不是一个简单聊天机器人，而是一套把多模态输入、知识检索、任务可靠性、故障流程和审计串起来的工业运维系统。

---

## 三个现场问题

### 问题一：现场信息碎片化

操作员可能通过文字描述现象、拍摄设备图片、录制异常声音，但这些信息通常分散在不同渠道，交接时容易丢失。

### 问题二：建议缺少可追溯依据

通用模型可以生成看似合理的答案，却不一定适用于当前组织、设备类型和具体型号，也可能把通用知识说成厂商手册结论。

### 问题三：诊断与处理脱节

得到建议以后，还需要确认故障、分派负责人、记录处理结果、验证和关闭。如果没有闭环，智能问答很难真正服务维修业务。

答辩表达：

> 我们把问题拆成三层：输入证据是否完整、知识依据是否可靠、处理过程是否闭环。系统设计分别对应多模态证据、RAG（检索增强生成）和故障状态机。

## 系统功能全景

建议在幻灯片上使用一条主链：

```text
文字 / 语音 / 图片
        ↓
结构化证据与设备上下文
        ↓
知识检索与确定性规则
        ↓
诊断建议与引用
        ↓
人工确认故障
        ↓
分派 / 处理 / 验证 / 关闭
        ↓
报告与审计
```

六项功能：

1. 多模态诊断；
2. 证据分区展示；
3. 知识库治理；
4. 故障处理闭环；
5. 异步报告中心；
6. 权限、通知与审计。

## 核心技术栈与持久化任务

| 层级 | 技术 |
|---|---|
| 前端 | `Vue 3`（渐进式前端框架）+ `TypeScript`（带类型的脚本语言）+ `Vite`（前端构建工具） |
| 后端 | `FastAPI`（Python 高性能接口框架）+ `Pydantic`（数据校验库） |
| 数据 | `SQLAlchemy`（对象关系映射工具）+ `SQLite`（嵌入式关系数据库）+ `Alembic`（数据库迁移工具） |
| 模型 | 千问云端兼容接口或 `Ollama`（本地模型运行器） |
| 语音 | `Faster-Whisper`（高效语音转文字实现） |
| 通信 | `SSE`（服务器发送事件） |
| 部署 | `Docker Compose`（多容器编排工具） |

为什么强调持久化任务：

- 接口快速返回，不被模型耗时阻塞；
- 浏览器刷新后可以恢复；
- 支持取消、重试和失败定位；
- 防止重复点击导致重复生成；
- 报告、语音、视觉和文本使用统一任务模型。

## 为什么模型不能直接给出故障结论

模型的输入具有局限：

- 图片只覆盖一个角度；
- 仪表可能反光或模糊；
- 设备外观无法证明内部状态；
- 通用知识不等于当前型号参数；
- 模型可能把常见故障当成当前故障。

系统的解决方法：

1. 先提取客观观察；
2. 异常必须关联观察或测量值；
3. 数值阈值和安全信号由代码规则检查；
4. 无证据时只给补充信息建议；
5. 故障必须由人员确认。

一句话：

> 模型负责解释，不负责替代业务授权。

## 现场输入怎样进入系统

1. 用户选择当前设备；
2. 文字、录音和图片在一个输入框中组合；
3. 发送时先保存用户消息和附件关系；
4. 接口创建后台任务并返回任务标识；
5. 后台任务按实际输入执行语音和视觉能力；
6. 最终结果与原附件一起进入会话历史。

强调：输入框中的预览只是发送前状态，真正可恢复的数据来自数据库消息关系和受保护的文件地址。

## 图片分析与语音转写

### 图片分析

- 校正 `EXIF`（可交换图像文件信息）方向；
- 控制尺寸，同时保留面板和仪表可读性；
- 先提取事实，再判断疑似异常；
- 使用 `Pydantic Schema`（Pydantic 数据结构约束）校验；
- 质量不足或无证据时进入人工复核。

### 语音转写

- 仅在存在音频时执行；
- 转写失败不清空图片和文字；
- 原音频保留在会话历史；
- 转写文本作为用户描述的补充，而不是覆盖用户原文。

---

## 人工智能结果不能直接写入业务事实

系统明确区分：

- 图片观察：当前画面实际可见；
- 知识事实：文档明确说明；
- 模型推断：可能原因或检查建议；
- 业务事实：人员确认后的故障和处理结果。

只有最后一类可以推动故障状态。模型生成的“疑似高温”不能直接把设备状态改成已确认故障。

---

## 确定性异常判断

代码规则负责：

- 温度、压力、电流等是否超过设备知识包范围；
- 是否出现报警灯、故障码和危险标志；
- 是否存在泄漏、裂纹、烧蚀、开盖或裸露带电部件；
- 图片设备类型是否与当前设备一致；
- 异常是否有对应观察证据；
- 模型与规则是否冲突。

规则输出仍是候选异常，不直接替代人工确认。

## 两条数据流，四层职责

### 两条数据流

诊断数据流：现场输入 → 证据 → 检索 → 回答。

业务数据流：诊断 → 故障 → 分派 → 处理 → 验证 → 报告。

### 四层职责

1. 前端层：输入、状态和证据展示；
2. 接口层：鉴权、校验、幂等和任务创建；
3. 后台任务层：模型、检索、报告和重试；
4. 业务与数据层：故障状态、知识版本、消息、附件和审计。

## 模型能力边界

模型可以：

- 提取图片中的可见信息；
- 整理语音和文字描述；
- 根据知识依据解释可能原因；
- 生成检查步骤和安全提醒。

模型不可以：

- 绕过组织和角色权限；
- 把无证据推断写成确定故障；
- 自动分派或关闭故障；
- 将通用资料冒充型号手册；
- 在模型失败时伪造“低置信度答案”。

## 总结

答辩收尾可以这样说：

> VoiceInspect 的创新点不是把多个模型简单拼接，而是建立了从现场证据到知识依据、从诊断建议到人工故障闭环的完整工程路径。系统通过持久化任务保证可靠性，通过结构化证据和确定性规则控制模型边界，通过权限和审计保证业务可用性。当前成果适合内部试点，但我们明确不把软件能力评测等同于真实现场准确率。
