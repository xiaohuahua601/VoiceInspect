## 1. 项目总览与技术栈

VoiceInspect 是一个面向工业设备运维的多模态辅助诊断平台。用户可以输入文字、上传现场图片或录制语音，系统把设备上下文、现场证据和知识库依据组合起来，生成带边界声明的诊断建议；有价值的诊断可以继续进入故障确认、负责人分派、处理、验证和关闭流程。

系统的核心定位不是“模型替代维修人员”，而是把分散的现场输入整理为可追踪证据，并让后续处理过程可审计、可恢复。

### 1.1 技术栈

| 层级 | 技术 | 在项目中的职责 |
|---|---|---|
| 前端 | `Vue 3`（渐进式前端框架）、`TypeScript`（带类型的脚本语言）、`Vite`（前端构建工具） | 页面、状态展示、流式回答、故障和知识管理 |
| 后端 | `FastAPI`（Python 高性能接口框架）、`Pydantic`（数据校验库） | 接口、权限、输入校验、任务提交 |
| 数据访问 | `SQLAlchemy`（对象关系映射工具）、`Alembic`（数据库迁移工具） | 持久化实体、查询和结构升级 |
| 数据库 | `SQLite`（嵌入式关系数据库） | 试点环境中的业务数据、任务和事件 |
| 异步执行 | `Worker`（后台任务进程）+ 数据库队列 | 执行语音、视觉、检索、生成和报告任务 |
| 文本模型 | 千问云端兼容 `OpenAI API`（OpenAI 风格应用程序编程接口）或本地 `Ollama`（本地模型运行器） | 诊断解释与建议生成 |
| 视觉模型 | 千问云端视觉模型或本地视觉模型 | 图片事实、读数和疑似异常提取 |
| 向量模型 | `bge-large-zh`（中文文本向量模型） | 知识切片向量化与相似度检索 |
| 语音识别 | `Faster-Whisper`（高效语音转文字实现） | 现场录音转写 |
| 流式通信 | `SSE`（服务器发送事件） | 向浏览器持续推送任务状态和回答片段 |
| 部署 | `Docker Compose`（多容器编排工具） | 分离运行网页、接口和后台任务进程 |

### 1.2 首期设备范围

- 空压机。
- 液压系统。
- 驱动电机。
- 通用加工设备。

设备类型不仅影响页面示例问题，还影响知识过滤、视觉提示、确定性规则和最终回答边界。

## 2. 整体架构

系统可以分为六层：

```text
交互层
  浏览器页面：诊断、会话、故障、知识库、报告、审计
        ↓
接口与权限层
  身份验证、角色权限、组织范围、参数校验、幂等校验
        ↓
持久化任务层
  BackgroundJob（后台任务）+ JobEvent（任务事件）+ CapabilityTask（能力任务）
        ↓
能力执行层
  STT（语音转文字）/ Vision（视觉分析）/ RAG（检索增强生成）/ LLM（大语言模型）/ Report（报告）
        ↓
业务闭环层
  诊断会话 → 故障确认 → 分派 → 处理 → 验证 → 关闭
        ↓
数据与文件层
  SQLite（嵌入式关系数据库）+ 上传文件 + 知识原文 + 报告文件
```

这套架构最重要的边界是：接口进程只负责接收和验证请求，耗时模型调用由后台任务进程完成。即使模型需要几十秒，页面和普通接口仍应保持可操作。

### 2.1 三条核心数据链

1. 诊断链：输入证据 → 能力任务 → 结构化观察 → 知识检索 → 诊断回答。
2. 故障链：诊断结论 → 人工确认 → 负责人处理 → 验证 → 关闭。
3. 审计链：关键写操作 → 审计事件 → 报告和追责查询。

## 3. 持久化任务队列在项目中的作用

### 3.1 为什么不能在接口请求里直接跑模型

模型推理、语音转写和报告生成都可能超过普通网页请求的耐心上限。如果全部同步执行，会出现：

- 接口工作线程长期占用；
- 浏览器刷新后结果丢失；
- 网络断开导致重复提交；
- 多次点击触发多个模型任务；
- 无法明确区分排队、运行、重试和失败。

因此项目使用数据库中的 `BackgroundJob`（后台任务）保存任务状态，用独立 `Worker`（后台任务进程）领取和执行。

### 3.2 任务状态机

```text
queued（已排队）
  → running（运行中）
      → retrying（重试中）→ running（运行中）
      → succeeded（成功）
      → partial（部分有效）
      → failed（失败）
      → cancelled（已取消）
```

`partial`（部分有效）只能用于“已经得到可展示的有效结果，但某个辅助能力失败”的情况。如果文本模型没有生成任何有效答案，任务必须标记为 `failed`（失败），不能伪装成低置信度诊断。

### 3.3 三类持久化对象

- `BackgroundJob`（后台任务）：保存任务类型、拥有者、载荷、结果、重试次数、租约和错误。
- `CapabilityTask`（能力任务）：保存语音、视觉、检索、文本生成等单能力状态。
- `JobEvent`（任务事件）：保存可按序号恢复的进度、片段和终止事件。

### 3.4 领取、租约和恢复

后台任务进程通过事务领取一条可执行任务并写入锁定时间。任务进程异常退出后，超过租约时间的任务可以重新进入队列。这样避免任务永久卡在“运行中”。本地试点默认只允许一个诊断任务占用模型资源，避免多个浏览器标签同时挤占显存和数据库写入。

### 3.5 幂等处理

浏览器为每次发送生成 `request_id`（请求幂等标识）。后端对“用户 + 请求标识”建立唯一约束。重复请求返回原任务，不重复写用户消息，也不重复调用模型。

## 4. 多模态诊断主流程详解

诊断入口不是把所有内容直接拼成一句提示词，而是按证据类型分阶段处理。

### 4.1 阶段一：请求接收与输入固化

接口首先检查：

- 用户是否登录；
- 用户能否访问当前组织和设备；
- 会话是否属于当前用户可访问范围；
- 附件是否存在且属于当前请求者；
- `request_id`（请求幂等标识）是否已经使用。

通过后，系统先保存用户消息以及 `MessageAsset`（消息附件关系），再创建后台任务。这样即使后续模型失败，用户文字、图片和语音仍可在刷新后恢复。

### 4.2 阶段二：语音转写

存在音频附件时才创建 `STT`（语音转文字）能力任务。转写成功后得到文本；失败时保留原音频，并把失败原因写入能力状态。没有音频时该阶段是 `skipped`（已跳过），不能被当成失败。

### 4.3 阶段三：视觉分析

存在图片附件时才执行视觉阶段：

1. 保留原图；
2. 根据 `EXIF`（可交换图像文件信息）校正方向；
3. 缩放到适合模型的尺寸；
4. 要求模型先提取客观事实，再判断疑似异常；
5. 用 `Pydantic Schema`（Pydantic 数据结构约束）校验输出；
6. 运行确定性规则；
7. 无观察证据或图片质量不足时标记 `needs_review`（需要人工复核）。

结构化视觉结果包含：

- 场景摘要；
- 设备类型；
- 图片质量；
- 可见观察；
- 仪表测量值；
- 疑似异常；
- 不确定项；
- 安全风险。

视觉模型不能因为“看起来像空压机”就断言内部故障。每个异常必须关联至少一条图片观察或读数。

### 4.4 阶段四：知识检索

系统使用“用户问题 + 语音转写 + 图片观察 + 当前设备信息”形成检索查询，只检索已发布、未停用、当前组织可访问并适用于当前设备的知识切片。

检索结果最多保留五条高相关依据。没有达到相关性阈值时返回“无可绑定依据”，而不是用低相关资料凑数。

### 4.5 阶段五：诊断生成

提示内容按以下区域组织：

```text
当前设备上下文
用户问题
图片客观观察
图片测量值
图片疑似异常
知识库依据
不确定性与安全限制
输出格式要求
```

`LLM`（大语言模型）负责组织语言、解释可能原因和建议检查顺序，不负责绕过权限，也不直接改变故障状态。

### 4.6 阶段六：流式保存与结束

模型片段先进入内存缓冲，达到片段数量或时间阈值后合并写入一个 `chunk`（内容片段）事件。完成、失败和取消前必须强制刷新缓冲区。这样既保留流式体验，又避免每个字都提交一次数据库。

最终回答保存为助手消息，原始 `Markdown`（轻量标记语言）文本保留在数据库。前端通过 `markdown-it`（标记语言解析器）渲染，并由 `DOMPurify`（网页内容清洗库）清理危险内容。

### 4.7 任务完成判定

- 用户没有提供图片，视觉阶段为“已跳过”，不影响整体成功。
- 用户没有提供语音，转写阶段为“已跳过”，不影响整体成功。
- 输入要求的能力均完成且回答正常生成，整体就是“完成”。
- 只有实际执行的某项能力失败、且仍存在有效结果时，才是“部分有效”。

## 5. 故障闭环状态机详解

### 5.1 状态流转

```text
new（新建）
  → confirmed（已确认）
  → in_progress（处理中）
  → pending_verification（待验证）
  → closed（已关闭）
```

### 5.2 角色职责

| 角色 | 主要权限 |
|---|---|
| 操作员 | 查看授权设备、发起诊断、补充现场处理说明；被分派时提交处理结果 |
| 维修主管 | 确认、分派、改派、审核处理结果、验证和关闭 |
| 知识管理员 | 导入、审核、发布、停用知识文档 |
| 系统管理员 | 全局账号、组织和故障管理 |

### 5.3 分派规则

负责人必须是故障设备所属组织中的在岗操作员或维修主管。禁用用户、其他组织用户、不在数据范围内的用户不能被分派。首次分派把故障从已确认推进到处理中；处理中允许改派，但不重复推进状态。

### 5.4 上一处理结果

每次确认、分派、处理、验证和关闭都写入 `fault_events`（故障事件）和 `audit_events`（审计事件）。详情页不仅展示状态，还应展示上一个处理人的说明、处理结果、验证依据和时间，保证接手人能理解前因后果。

### 5.5 关闭门槛

没有故障位置、现场证据、处理结果和验证依据时不允许关闭。模型建议只能作为辅助材料，最终关闭必须由有权限的人执行。

## 6. 核心能力与接口体系

### 6.1 会话能力

- 创建和查询诊断会话；
- 保存用户消息、助手消息与附件关系；
- 删除单个会话或批量删除；
- 删除时保留已经形成的故障记录，并解除会话关联；
- 活跃任务存在时阻止删除，避免运行中数据悬空。

### 6.2 附件能力

- 校验文件扩展名、媒体类型、文件签名、大小、图片像素和音频时长；
- 使用随机文件名保存，避免路径穿越；
- 下载和预览时再次校验权限；
- 发送成功后从输入区移除，并在对话时间线中展示。

### 6.3 任务能力

主要接口包括：

- `GET /api/v1/jobs/{id}`：查询任务；
- `POST /api/v1/jobs/{id}/cancel`：取消任务；
- `POST /api/v1/jobs/{id}/retry`：重试任务；
- `GET /api/v1/sessions/{id}/events`：恢复会话事件。

### 6.4 报告能力

会话报告和故障报告通过后台任务生成。报告成功后才允许下载；生成、失败和下载都写审计事件。报告包含设备、会话、证据、知识引用、故障处理和审计信息。

### 6.5 通知能力

负责人收到平台内通知。通知支持单条已读、一键全部已读，并可直接跳转到对应故障详情。

## 7. RAG（检索增强生成）实现

### 7.1 为什么需要知识检索

通用模型知道一般维修常识，但不知道企业当前设备、已发布资料和组织边界。知识检索的作用是把回答约束在可追溯材料中，并返回来源、版本、章节、页码和片段。

### 7.2 文档生命周期

```text
uploaded（已上传）
  → parsed（已解析）
  → indexed（已建立索引）
  → published（已发布）
  → disabled（已停用）
```

只有 `published`（已发布）且未停用的文档参与诊断检索。

### 7.3 文档分类

- `manufacturer_manual`（制造商手册）；
- `maintenance_guide`（维护指南）；
- `safety_guidance`（安全指导）；
- `fault_case`（故障案例）；
- `dataset_card`（数据集说明卡）；
- `image_case`（图片案例）。

其中数据集说明卡只解释数据来源、字段和算法适用范围，不能直接作为维修结论依据。

### 7.4 过滤顺序

检索前先做数据库过滤：

1. 组织范围；
2. 发布状态；
3. 停用状态；
4. 文档分类；
5. 通用资料或当前设备型号；
6. 当前设备类型。

权限过滤必须发生在相似度排序之前，避免先检索到越权内容再在页面隐藏。

### 7.5 向量检索与降级

正常路径使用向量模型把查询与知识切片转换为向量，计算 `cosine similarity`（余弦相似度）。当向量服务暂时不可用时，系统只在相同权限和设备过滤结果中执行中文二元词组的词法回退；回退不是全库模糊匹配，也不会降低发布和组织边界。

### 7.6 引用回溯

每条引用至少保留：来源标题、原始地址、版本、机构、许可证、设备范围、章节、页码、原始片段和哈希值。通用资料必须标记为通用依据，不得伪装成具体型号手册。

## 8. 确定性异常规则

模型擅长读取复杂画面和生成解释，代码更适合执行稳定边界。因此项目把二者分工：

- 模型提取“屏幕显示 118℃”“地面存在深色液体痕迹”等事实；
- 规则根据设备知识包判断是否超过范围、是否存在安全信号；
- 最终回答仍使用“疑似”“建议确认”等表述。

首期规则包括：

- 温度、压力、电流是否超出知识包范围；
- 是否出现报警灯、故障码或危险标识；
- 是否存在泄漏、裂纹、烧蚀、开盖或裸露带电部件；
- 图片设备类型与当前选择设备是否一致；
- 每个异常是否关联实际观察证据；
- 结论是否引用了图片字段或知识依据。

规则与模型冲突时，系统进入人工复核，而不是选择更“自信”的一方。

## 9. 人工确认与故障处置

诊断建议转换为故障时，应由用户确认故障现象、位置、严重级别和证据。原因有三点：

1. 图片只能覆盖有限角度；
2. 通用资料不能替代型号手册；
3. 错误工单会影响维修资源和生产安排。

因此系统坚持“模型生成建议，人员确认业务事实”。故障进入闭环后，模型不能自行分派、验证或关闭。

## 10. 安全体系

### 10.1 身份与会话

- 强密码与首次登录改密；
- 登录失败锁定；
- 访问令牌刷新、退出和主动吊销；
- 并发会话管理；
- 禁用账号立即失去访问能力。

### 10.2 RBAC（基于角色的访问控制）

接口层根据角色和组织范围共同授权。前端隐藏按钮只是体验优化，不能代替后端校验。

### 10.3 文件安全

系统不信任浏览器上报的媒体类型，会结合文件头和内容校验。文件使用服务端生成名称，禁止用户路径进入真实磁盘路径。

### 10.4 网页安全

- `CSP`（内容安全策略）限制脚本和资源来源；
- `CORS`（跨来源资源共享）限制允许的前端地址；
- `DOMPurify`（网页内容清洗库）过滤脚本、事件属性和危险协议；
- 用户原始输入始终按纯文本显示。

### 10.5 审计

审计事件保存用户、动作、对象、时间、结果和 `trace_id`（链路追踪标识）。敏感字段、密钥和完整模型提示不能写入日志。

---

## 11. SSE（服务器发送事件）与前端交互

### 11.1 事件契约

常见事件包括：

- `status`（状态）：阶段开始、排队或重试；
- `chunk`（内容片段）：合并后的回答文字；
- `capability`（能力状态）：语音、视觉、检索等结果；
- `error`（错误）：可展示的错误编码和阶段；
- `[DONE]`（流结束标志）：明确结束连接。

前端必须先判断 `[DONE]`（流结束标志），不能把它当作 `JSON`（JavaScript 对象表示法）解析。

### 11.2 断线恢复

每个任务事件都有递增序号。浏览器记住最后序号，重连时只请求后续事件；刷新页面后根据任务标识恢复，而不是重新提交诊断。

### 11.3 页面状态

前端分别展示：排队中、分析图片、检索资料、生成回答、重试中、已完成、部分有效和失败。失败时保留输入附件，并提供明确重试入口。

## 12. 六条端到端业务流程

### 12.1 纯文字诊断

用户选择设备并提问 → 保存消息 → 创建任务 → 跳过语音和视觉 → 检索适用知识 → 生成回答 → 保存引用和消息 → 推送结束事件。

### 12.2 文字加图片诊断

上传图片 → 附件进入输入区 → 与文字一次发送 → 图片关系先保存 → 视觉模型提取观察 → 规则复核 → 知识检索 → 生成分区回答 → 图片显示在历史消息中。

### 12.3 语音加图片诊断

录音和图片同时附加 → 一次发送 → 语音转写与视觉分析分别记录能力状态 → 合并为同一个诊断上下文 → 任一辅助能力失败时保留另一能力结果。

### 12.4 诊断转故障

用户查看证据 → 人工补充故障位置和现场依据 → 创建故障草稿 → 维修主管确认 → 选择同组织在岗负责人 → 进入处理。

### 12.5 故障处理与验证

负责人查看上一人的处理说明 → 填写处理结果和前后证据 → 提交待验证 → 维修主管核实 → 填写验证依据 → 关闭。

### 12.6 报告生成

用户发起报告 → 接口创建报告记录和后台任务 → 任务读取授权数据并生成文件 → 成功后开放下载 → 下载时再次鉴权并记录审计。

## 13. 关键工程决策与踩坑

### 13.1 模型成功不等于任务成功

曾出现图片已识别，但最终仍显示“图片失败”或“部分完成”。根因通常是能力状态和总任务状态混用。正确做法是只统计实际请求的能力，并把“需要人工复核”与“技术失败”分开。

### 13.2 流式输出不能逐字提交数据库

逐片段提交会造成数百次事务，并与事件轮询竞争。改为内存缓冲和批量写入后，页面仍能持续显示，但数据库压力显著降低。

### 13.3 附件必须先建立消息关系

如果只在输入框保存临时预览地址，刷新后图片会消失。附件上传、消息关联和用户消息必须先持久化，发送成功后再清空输入区。

### 13.4 云端文本模型不代表视觉自动可用

文本和视觉虽然可以使用同一模型系列，但请求消息结构不同。图片必须以模型支持的多模态内容格式传入，并由后台进程读取真实文件；只把文件名拼进提示词会得到“未提供图片”的错误回答。

### 13.5 知识存在不等于可检索

文档可能因为未发布、已停用、组织不匹配、设备范围不匹配、切片为空或向量失败而无法命中。排查必须同时检查文档、切片、索引、过滤条件和最终引用。

### 13.6 操作员被分派后必须有可执行动作

“可分派给操作员”与“操作员完全只读”相互矛盾。系统需要明确：操作员不能确认、改派、验证或关闭，但被分派后可以提交现场处理结果。

### 13.7 每次代码修改后更新容器

浏览器访问的是容器内构建产物。本地源文件改变并不等于页面已经改变。完成修改后必须重新构建并重启对应服务，再以容器健康和页面行为验证。

## 14. Docker（容器编排平台）部署

### 14.1 服务划分

- `web`（网页服务）：提供编译后的前端；
- `api`（接口服务）：处理鉴权、业务接口和任务提交；
- `worker`（后台任务服务）：执行模型、检索和报告任务。

三个服务使用同一业务代码版本，并共享数据库、上传目录、知识目录和报告目录。接口服务启动前执行 `Alembic`（数据库迁移工具）升级，后台任务服务等待依赖健康后启动。

### 14.2 配置原则

模型地址、模型名、密钥、数据库密码等只通过环境变量注入。密钥不得进入前端、源码、日志、镜像层或文档示例中的真实值。

### 14.3 持久化范围

备份必须覆盖：数据库、上传文件、知识原文、向量索引、日志和报告文件。只备份数据库不能恢复图片和报告。

## 15. 性能观测与质量指标

每个诊断任务记录：

- 队列等待时间；
- 向量计算耗时；
- 知识查询耗时；
- 首个输出片段耗时；
- 文本生成总耗时；
- 输入和输出令牌数；
- 模型加载、提示评估和生成耗时；
- 模型名、处理器类型和重试次数；
- 数据库片段写入数量。

这些指标用于区分模型加载慢、向量模型争用、生成慢、数据库写入慢和重复请求，不能只看用户感知的“卡”。

质量门禁包括：结构化视觉输出合法率、设备类型识别率、异常召回率、正常图片误报率、引用有效率、无证据时的拒绝确定性结论、知识检索召回率和首段输出耗时。

---

## 16. 可解释性与交互设计

诊断回答按证据分区，而不是只给一大段文本：

- 图片直接观察；
- 仪表读数；
- 疑似异常；
- 知识库事实；
- 可能原因；
- 推荐检查；
- 安全措施；
- 不确定性；
- 引用依据。

“置信度”属于单条观察或异常的属性，不应在整个回答顶部机械显示“低置信度”。整体状态表达任务是否正常完成，证据区表达哪些结论仍需人工确认，两者不能混为一谈。

---

## 17. 数据来源与边界

正式知识优先使用许可明确的政府、标准机构和公开维护资料。厂商型号手册只有在用户有权使用时才进入本地私有知识库，不提交公共仓库。

公开数据集用于算法理解、字段说明和评测，不直接充当维修手册。合成图片、公开图片和用户现场图片分开统计，不能混合后宣称现场准确率。

项目当前可声明“具备内部真实业务试点的软件能力”，但不能声明：

- 已通过真实现场诊断准确率验收；
- 已接入企业单点登录；
- 已接入外部维修或生产系统；
- 已完成多节点高可用部署。

## 18. 附录：一次诊断的事件时间线

以下时间线帮助读者把页面、接口、后台任务和数据库联系起来：

```text
T0   用户选择空压机 A-01，附加图片并输入现象
T1   前端生成 request_id（请求幂等标识）并提交
T2   接口校验权限、附件和会话
T3   保存用户消息与图片关系
T4   创建 BackgroundJob（后台任务）并返回任务标识
T5   Worker（后台任务进程）领取任务
T6   Vision（视觉分析）输出观察、读数和疑似异常
T7   Rule Engine（规则引擎）检查证据关联和阈值
T8   RAG（检索增强生成）返回最多五条适用依据
T9   LLM（大语言模型）开始生成，首个 chunk（内容片段）写入事件表
T10  浏览器通过 SSE（服务器发送事件）持续显示回答
T11  完整助手消息、引用和任务结果保存
T12  发送 [DONE]（流结束标志），页面显示“完成”
T13  用户刷新页面，消息和图片从数据库重新加载
```

理解这条时间线后，就能回答项目最核心的问题：VoiceInspect 不是一个简单的聊天页面，而是一套把现场证据、模型能力、知识依据、任务可靠性和人工故障闭环连接起来的工业运维系统。
